\section{Executive Summary}

We built a fully operational \textbf{Distributed Benchmarking and Hosting Platform} that automates the entire lifecycle of evaluating contestant-submitted trading infrastructure: from code upload and containerised sandbox deployment, through a 1{,}000-bot concurrent load test, to real-time composite scoring on a live leaderboard.

The platform demonstrates:
\begin{itemize}[leftmargin=1.5em]
  \item \textbf{Sandboxing depth} — Docker + Kubernetes with seccomp profiles, CPU pinning, and network isolation
  \item \textbf{FIX 4.4 protocol support} — signals deep domain knowledge of financial exchange infrastructure
  \item \textbf{Real tail-latency measurement} — HDR histograms reporting p50/p90/p99, never just averages
  \item \textbf{Price-time priority correctness validation} — fill accuracy and order-book integrity checks
  \item \textbf{One-command reproducible deploy} — \texttt{make up} spins the entire platform in~$\approx$12 minutes
  \item \textbf{Live Grafana observability} — auto-provisioned dashboards for latency, TPS, score, and correctness
\end{itemize}

\section{Key Engineering Decisions}

\subsection{HDR Histograms for Latency}
We use HdrHistogram (High Dynamic Range) rather than simple averages. Every latency report publishes p50, p90, and p99 percentiles. This exposes tail latency that averages hide, which is critical for evaluating a matching engine under load.

\subsection{FIX 4.4 Protocol}
The bot fleet sends orders using FIX 4.4 (via QuickFIX/Go) alongside REST and WebSocket. FIX is the industry-standard wire protocol for financial exchange communication. Supporting it demonstrates genuine domain understanding beyond a basic REST mock.

\subsection{Price-Time Priority Validation}
The telemetry service includes a correctness validator that verifies every fill against price-time priority rules. Fill accuracy and order-book integrity are first-class scoring dimensions shown on the leaderboard, not just latency and throughput.

\subsection{Telemetry Startup Resilience}
\texttt{telemetry/cmd/main.go:connectStore()} retries the TimescaleDB connection with exponential backoff (2s → 4s → 8s → 16s cap) for up to 90 seconds. This eliminates the pod startup race condition where DNS resolution for the TimescaleDB StatefulSet was not yet available, removing the need for manual \texttt{kubectl rollout restart}.

\subsection{One-Command Deploy}
\begin{lstlisting}
make up    # kind cluster + Helm deploy + Kafka topics (~12 min)
make bench # spawn 1000 bots across 3 teams
\end{lstlisting}
Tested from a clean state. No manual steps required.

\section{Scoring Model}

The composite score visible on the leaderboard combines four dimensions:

\begin{center}
\begin{tabular}{L{4cm} C{2cm} L{7cm}}
  \toprule
  \textbf{Dimension} & \textbf{Weight} & \textbf{Metric} \\
  \midrule
  Latency (p99)     & 35\%  & Lower is better; HDR histogram p99 \\
  Throughput (TPS)  & 25\%  & Orders processed per second \\
  Correctness       & 30\%  & Fill accuracy + price-time priority \\
  Availability      & 10\%  & Uptime during load test window \\
  \bottomrule
\end{tabular}
\end{center}

Scores are published to \texttt{bench.scores} Kafka topic and streamed to the React leaderboard via WebSocket within $<$1 second of computation.
